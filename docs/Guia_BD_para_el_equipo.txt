2. QUÉ ES UNA MIGRACIÓN Y QUÉ NO SE DEBE HACER
================================================================================================
Una MIGRACIÓN es un archivo PHP (carpeta database/migrations) que describe cómo crear una tabla.
Es el 'control de versiones' de la base de datos: todos corremos las mismas migraciones y
tenemos las mismas tablas. Un MODELO (carpeta app/Models) es la clase PHP que representa una
tabla: con Gasto::create(...) guardas un gasto sin escribir SQL. Una SEMILLA (seeder) mete datos
iniciales. Una FÁBRICA (factory) inventa datos de prueba.

REGLAS PARA NO ROMPER LA BASE DEL EQUIPO:
   - NO edites una migración que ya está en main. Si necesitas una columna nueva o cambiar algo:
     php artisan make:migration agregar_algo_a_gastos --table=gastos  y escribe el cambio ahí.
     Avísame en el grupo (los demás deberán correr php artisan migrate).
   - NO subas database.sqlite ni .env a Git (ya están en .gitignore). Cada quien tiene su base
     local.
   - NO crees tablas nuevas sin avisar: todas las que necesitamos ya existen (ver sección 4).
   - Si crees que falta una columna, abre una tarjeta 'Pedido a Juan' en Jira con: qué
     necesitas, para qué tarea (ID) y para cuándo.

3. MAPA DE LAS TABLAS (CÓMO SE CONECTAN)
================================================================================================

  Lectura: "A ──< B" significa que UN registro de A tiene MUCHOS de B (B guarda la llave de A).
  Todo cuelga de USERS: casi cada tabla tiene user_id.

        users ──< categorias (propias; user_id vacío = del sistema)
          │
          ├──< gastos            (cada gasto tiene UNA categoria_id)
          │
          ├──< gastos_fijos      (también con categoria_id)
          │        └──< pagos_gasto_fijo ──< notificaciones   (una alerta puede apuntar a un pago)
          │
          ├──< simulaciones_credito
          │
          ├──< informes ──< detalles_informe
          │
          ├──< notificaciones    (también puede apuntar a una meta: p. ej. una invitación)
          │
          └──< metas (creador) ──< participaciones_meta   (quién participa: máximo 2)
                         └─────< aportes_meta             (cuánto aportó cada uno: PRIVADO)

  Relaciones, una por una (padre ──< hijos):
     users              ──<  categorias             1 a muchas (opcional)
     users              ──<  gastos                 1 a muchas
     categorias         ──<  gastos                 1 a muchas
     users              ──<  gastos_fijos           1 a muchas
     categorias         ──<  gastos_fijos           1 a muchas
     gastos_fijos       ──<  pagos_gasto_fijo       1 a muchas
     users              ──<  pagos_gasto_fijo       1 a muchas
     pagos_gasto_fijo   ──<  notificaciones         1 a muchas (opcional)
     users              ──<  notificaciones         1 a muchas
     metas              ──<  notificaciones         1 a muchas (opcional)
     users              ──<  simulaciones_credito   1 a muchas
     users              ──<  informes               1 a muchas
     informes           ──<  detalles_informe       1 a muchas
     users              ──<  metas                  1 a muchas (creador)
     metas              ──<  participaciones_meta   1 a muchas
     users              ──<  participaciones_meta   1 a muchas
     metas              ──<  aportes_meta           1 a muchas
     users              ──<  aportes_meta           1 a muchas

  Qué pasa al BORRAR:
     - Se borra un usuario        -> se borran TODOS sus datos (gastos, gastos fijos, pagos, simulaciones,
                                     informes, notificaciones, metas que creó, aportes y participaciones).
     - Se borra una categoría     -> NO se puede si tiene gastos o gastos fijos (primero se mueven; N2).
     - Se borra un gasto fijo     -> se borran sus pagos.
     - Se borra un informe        -> se borran sus detalles.

5. QUÉ CAMBIÓ RESPECTO AL DIAGRAMA ORIGINAL Y POR QUÉ
================================================================================================
  ANTES                     AHORA                       POR QUÉ
  Tabla saldo               ELIMINADA                   El saldo guardado se desactualiza. Se CALCULA: disponible del
                                                        mes = ingreso - gastos (decisión #14).
  Tabla cuota_credito       ELIMINADA                   El crédito es solo simulación (decisión #4). Una tabla de cuotas
                                                        implicaría alertas y pantallas que no están planeadas.
  credito                   simulaciones_credito        Se quitó el 'cupo' (nadie lo usa) y se agregaron cuota,
                                                        total_pagar e intereses, que calcula el servidor.
  Dinero                    enteros                     NUMBER(12,2) con decimales se guarda como número flotante en
                                                        SQLite y da errores de redondeo. Pesos enteros siempre.
  informe_mensual           informes                    La llave era solo la fecha: dos usuarios con informe del mismo
                                                        mes chocaban. Ahora tiene id propio y es único por (usuario,
                                                        año, mes).
  detalle_informe           detalles_informe            Guarda el nombre y el bloque de la categoría como 'foto' para
                                                        que el historial no cambie si luego la renombran o borran.
  pago_gasto_fijo           + gasto_fijo_id             Faltaba saber de qué gasto fijo es cada pago (decisión #9).
                                                        Único por (gasto fijo, periodo): no se paga dos veces el mismo
                                                        mes.
  meta_ahorro               metas                       Se quitó monto_actual (el avance se calcula sumando aportes, y
                                                        así no se desincroniza ni se filtra el aporte ajeno). Se agregó
                                                        creador_id y fecha_limite.
  ahorro_individual         aportes_meta                Tenía un id 'UNKNOWN' y sin llave primaria. Ahora es una tabla
                                                        normal con su llave.
  participacion_meta        participaciones_meta        Ahora tiene llave primaria y es única por (meta, usuario): no se
                                                        invita dos veces a la misma persona.
  notificacion              notificaciones              Referencias opcionales (a un pago o a una meta) y clave_unica
                                                        para que el comando diario de alertas no duplique.
  usuario                   users                       Nombres que Laravel espera: users, email, password. En pantalla
                                                        se sigue viendo 'Correo' y 'Contraseña'.
  usuario (cédula)          + cedula                    Decisión #1: se guarda la identificación.
  usuario (estado)          activo                      Verdadero/falso. false = cuenta suspendida (el middleware la
                                                        expulsa).
  usuario (consentimiento)  + consentimiento_datos_at   Fecha en que aceptó el tratamiento de datos; el registro (J3) la
                                                        exige.
  categoria_gasto           categorias (+ bloque)       Decisión #12: cada categoría pertenece a un bloque 50/30/20
                                                        (necesidades, discrecionales, ahorro).
  gasto_fijo                + periodicidad, activo      Decisión #6: solo 'mensual'; y se puede desactivar sin borrar.
  Estados                   texto                       necesidades, pendiente, pagado, etc. son texto validado en la
                                                        aplicación, no enum (SQLite no los maneja bien).

Todo esto quedó anotado con fecha en DECISIONES.md y en el diccionario de datos docs/backend/03-migraciones.php.

8. REGLAS DE ORO
================================================================================================
   - DINERO = ENTEROS en pesos. Nunca float ni decimales. Se formatea solo al mostrarlo.
   - TODA consulta de datos financieros parte del usuario autenticado (delUsuario(auth()->id())
     o $usuario->gastos()). Nunca Gasto::all() en una pantalla. Se prueba siempre con DOS
     usuarios.
   - El user_id SIEMPRE sale de la sesión, nunca de un campo del formulario.
   - Usa $request->validated() (FormRequest), nunca $request->all() para guardar.
   - rol y activo NO se asignan en masa en User (a propósito): no los pongas en $fillable.
   - Privacidad de metas (RQNF-03): jamás enviar a una vista, JSON o tooltip el aporte
     individual de la otra persona.
   - Las fechas usan la zona America/Bogota (ya está en config/app.php). No uses fechas UTC a
     mano.
   - Los mensajes de error y éxito son los EXACTOS de la guía de cada pantalla.
   - Antes de pedir la unión a main: php artisan test debe pasar completo.

10. PROBLEMAS COMUNES Y SU SOLUCIÓN
================================================================================================
   - 'APPLICATION IN PRODUCTION' al correr migrate: tu .env tiene APP_ENV=production. Cámbialo a
     local (y APP_DEBUG=true).
   - No se crearon los usuarios de prueba: mismo motivo (APP_ENV distinto de local).
   - 'table ... already exists' o columnas que no aparecen: tienes una base vieja. php artisan
     migrate:fresh --seed.
   - 'Database file ... does not exist': crea el archivo vacío (Git Bash: touch
     database/database.sqlite) y repite.
   - 'SQLSTATE[23000] ... UNIQUE constraint failed': intentaste guardar algo repetido (correo,
     cédula, pago del mismo mes, invitación repetida). Es la regla funcionando.
   - 'FOREIGN KEY constraint failed': apuntas a un id que no existe, o borras algo que tiene
     hijos (una categoría con gastos).
   - 'Class ... not found': falta el archivo o hay que correr  composer dump-autoload.
   - 'Add [campo] to fillable property': el campo no está permitido en ese modelo. En User solo:
     nombre, cedula, email, password, ingreso_mensual, consentimiento_datos_at.
   - Las pruebas borran mis datos de desarrollo: no debería pasar (usan una base en memoria).
     Revisa que phpunit.xml tenga DB_CONNECTION=sqlite y DB_DATABASE=:memory: sin comentar, y
     avísame.
   - Algo distinto: copia el mensaje COMPLETO del error y mándalo al grupo con la plantilla de
     bloqueo.
